Product intent

Wasselne is an on-demand transport platform inspired by Uber, Careem, Bolt, and regional taxi services. A rider can locate nearby eligible vehicles, choose a category (car, motorcycle, or tuk-tuk), set pickup and destination, see a fare estimate, request a ride, see the assigned driver's live location and route, communicate with the driver, and contact support. A driver can register with photos and documents, become available after approval, receive nearby offers, accept or decline them, navigate to pickup and destination, communicate with the rider, and contact support. Admins review drivers, configure operational data, handle trips and support, and see relevant live status. Chat must support translation while preserving the original message.

Bus service is an open product decision. A scheduled bus with routes, stops, seats, and timetables requires different flows from on-demand car/motorcycle/tuk-tuk dispatch. The Claude Code prompt must require Claude to clarify which bus model is intended and whether buses are in the first release. It must never silently implement a bus as a large taxi or silently drop the requirement. It may recommend a later bus module if the user approves.

Architectural baseline to preserve

Architecture: TypeScript/NestJS modular monolith with explicit auth, rider, driver, vehicle, dispatch, trip, pricing, payment/ledger, chat/translation, support, notification, and admin boundaries. HTTP API, WebSocket gateway, and background workers can be separate processes from one codebase. Use at least two application instances behind a load balancer in production, not as a requirement for local development.

Mobile: Two separately installable Flutter/Dart applications with shared packages for models, API, design tokens, and carefully chosen reusable UI. Driver background location requires platform-specific Android/iOS configuration and testing; Flutter alone does not solve it.

Admin: React/Next.js with TypeScript. It is an operations console, not a generic page-content CMS. Include role-based permissions and an audit trail.

Durable records: Managed PostgreSQL with PostGIS for identities, driver and vehicle approvals, documents' metadata, offers, trips and transitions, prices, financial records, chat, tickets, zones, and audit data.

Ephemeral state: Managed Redis with GEOSEARCH for currently eligible nearby drivers and short-lived presence/location data. Check timestamps, heartbeat freshness, availability, vehicle category, and approval before dispatch. Redis is not the source of truth for trip ownership or money. Avoid making Redis lock ownership the sole defense against double assignment.

Dispatch: Shortlist candidates by category and location, use road ETA for a small shortlist, create offers with expiry and configurable fan-out, and let exactly one eligible driver win. Validate offer, trip, and driver state and reserve/accept atomically in PostgreSQL; use conditional updates, transactions, appropriate constraints, and idempotency keys. Explicitly handle concurrent acceptances, repeated requests, timeouts, cancellations, and worker crashes.

Live experience: WebSockets for foreground location, trip events, and chat; FCM/APNs notifications for background offers. On reconnection, obtain an authoritative trip snapshot and resume from server-side state. Neither a socket packet nor a push notification guarantees an offer was accepted or delivered.

Maps and navigation: Begin with a commercial map and routing provider such as Google Maps/Routes, subject to coverage, vehicle-mode suitability, licensing, and cost validation in the launch area. Use in-app maps and route display for rider and driver; decide through product discovery whether driver turn-by-turn navigation starts with external-map deep links or an embedded navigation SDK. Do not conflate straight-line proximity with road ETA or claim external navigation is cost-free in all contexts.

Files: Private S3-compatible object storage for driver registration photos/documents, preferably direct uploads via short-lived signed URLs; record metadata and review status in PostgreSQL. Restrict access and retention.

Communication: Trip-scoped chat in PostgreSQL; translate on demand and retain the original and language information. Link support tickets to trips and expose safe rider/driver contact options. Evaluate local masked calling and emergency/SOS needs before implementation.

Infrastructure: Containerized deployment in a region close to the initial market, multiple availability zones, managed Postgres with backup/failover, managed Redis, object storage, secret management, health checks, CI/CD, staging, logging, metrics, tracing, alerting, and restore drills. Start with a managed container service; no Kafka, Kubernetes, H3, NoSQL chat database, or dedicated Go matching service without a measured reason.

The baseline is an initial recommendation, not permission to invent vendor account details, local regulations, fare formulas, launch country/city, payment providers, or feature priority. Require Claude to surface and resolve consequential unknowns with me before implementing their dependent phases. Choose concrete versions, plugins, SDKs, and cloud services only after checking their current documentation and compatibility when implementation begins. Document decisions and trade-offs.
